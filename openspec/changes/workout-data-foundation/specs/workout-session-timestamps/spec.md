# Workout Session Timestamps Specification

## Purpose

The temporal columns a training session needs: nullable session boundary timestamps on `Workout` that
land unwired for a later phase to populate, record timestamps on `Workout` and `Exercise`, and the
standing rule that `Workout.date` — not any insertion timestamp — is the authoritative date a workout was
performed.

## Requirements

### Requirement: Session boundary columns exist, nullable and unwritten

`Workout` MUST carry nullable session start and end timestamps. This change MUST NOT wire them into the
creation form or the creation action, so a workout created by this change MUST have both null. No
user-facing behavior MAY depend on them yet.

#### Scenario: Created workout leaves both boundaries null

- GIVEN a workout is created through the creation form
- WHEN the persisted workout is read
- THEN its session start timestamp is null
- AND its session end timestamp is null

#### Scenario: Columns accept null

- GIVEN the workout schema and its applied migrations
- WHEN the session boundary columns are inspected
- THEN both are nullable
- AND neither carries a non-null default

#### Scenario: No surface reads the boundaries

- GIVEN a workout with null session boundaries
- WHEN any list, detail, dashboard or summary surface renders it
- THEN it renders without error and without referencing either boundary

### Requirement: Record timestamps on workouts and exercises

`Workout` and `Exercise` MUST each carry a creation timestamp and a last-update timestamp, both populated
by the data layer without the application supplying a value. The last-update timestamp MUST advance when
the row is updated. Both MUST be defaulted so the migration applies to a non-empty table without
hand-written SQL.

#### Scenario: Creation timestamps are populated automatically

- GIVEN a workout is created without explicit timestamps
- WHEN it is read back
- THEN its creation timestamp and last-update timestamp are both non-null

#### Scenario: Update advances the last-update timestamp

- GIVEN an existing exercise with a recorded last-update timestamp
- WHEN the exercise row is updated
- THEN its last-update timestamp is later than the previously recorded value
- AND its creation timestamp is unchanged

#### Scenario: Migration applies to existing rows

- GIVEN a database already holding workout and exercise rows
- WHEN the migration adding these columns is applied
- THEN it succeeds without a hand-edited step
- AND existing rows receive the default timestamp

### Requirement: Workout.date is the authoritative performance date

`Workout.date` MUST remain the single authoritative date on which a workout was performed. Listing,
sorting, display and any future progress metric MUST use it. No consumer MAY use a set's insertion
timestamp or a workout's creation timestamp as the performance date, because those record when the row
was written, not when the training happened.

#### Scenario: A back-dated workout displays its performed date

- GIVEN a workout created today whose date is set to a day last week
- WHEN the workout list and the workout detail render it
- THEN both show last week's date
- AND neither shows today's insertion timestamp

#### Scenario: Sorting is unchanged by the new timestamps

- GIVEN several workouts with differing dates and differing insertion timestamps
- WHEN the workout list is ordered
- THEN it is ordered by `Workout.date` exactly as it was before this change

#### Scenario: A set's insertion timestamp is not a performance date

- GIVEN a workout whose sets share one insertion timestamp
- WHEN any consumer needs the date the training happened
- THEN it reads `Workout.date`, not the set insertion timestamp

### Requirement: No session boundary ordering constraint in this change

Because nothing writes the session boundaries in this change, no database-level check constraint
enforcing that the end timestamp is not earlier than the start timestamp MAY be introduced here. The
phase that wires these columns SHALL own that validation.

#### Scenario: No check constraint is added

- GIVEN the generated migration for this change
- WHEN its statements are inspected
- THEN it adds no check constraint relating the two session boundary columns

### Requirement: Exactly one generated migration

All schema changes in this capability and its sibling capabilities MUST land in exactly one migration
folder generated by the migration tool, committed together with the schema file. That migration MUST NOT
be hand-edited, and no data backfill MAY be performed — the development database is reset instead.

#### Scenario: One migration folder is added

- GIVEN this change is applied
- WHEN the migrations directory is inspected
- THEN exactly one new migration folder exists
- AND the schema file change is committed alongside it

#### Scenario: Migration is not hand-edited

- GIVEN the generated migration
- WHEN its contents are compared with the tool's output for the schema change
- THEN they are identical
